The Learning Agent

The learning agent bench measures whether an agent can run the full applied-ML loop — build training data, train a model, evaluate it, and iterate — well enough to make a small model answer expert questions in a domain neither model has seen. There is no verifiable reward and no human in the loop.

Objective

A learning agent (a frontier model driving a CLI coding harness) receives a domain corpus and a frozen student model. Within a fixed wall-clock budget it must produce a fine-tune of the student, plus the inference harness the student answers through. The goal is the highest possible score on held-out expert questions about the corpus.

The agent controls every step of the loop:

  1. Training-data construction.
  2. Training method and hyperparameters.
  3. Its own development evaluation.
  4. The answering system.

Nothing is delegated and nothing is graded by unit tests. Answers are scored by a pinned LLM rubric judge.

The reported number is the margin: the trained student's held-out score minus the untrained student's score through a fixed reference harness, both judged identically. Gains that do not transfer to unseen questions do not raise the margin.

The three actors

actorwhat it iswhat it holds
Learning agent a frontier model (Claude, GPT, GLM, Kimi, …) in a CLI harness (Codex CLI, Claude Code, OpenCode), launched in an isolated copy of this repository the workspace: corpus, the learning toolbox, trainers, its own dev evaluation data. The agent may rewrite anything in the workspace.
Student the small model being taught — pinned in bench/config.yaml (global.base_model, currently Qwen3.5-9B) nothing. Every model that answers at evaluation time must be the student or a fine-tune of it; no external LLM API may sit in the answer path.
Operator the human (or automation) that launches runs and scores submissions the held-out questions and gold (physically absent from every workspace), the pinned judge, and the submission contract.

The submission contract

When the budget ends, the workspace is the submission. The operator runs, from the workspace root, exactly:

python submission/eval.py --input questions.json --output answers.json

The contract:

  1. Input is a JSON array of {"id", "question"}.
  2. Output is a JSON object {id: answer} covering every input id.
  3. The command must run unattended. If it does not, there is nothing to score.
  4. The agent's eval.py must handle its own serving (typically the merged weights on the shared Modal volume).
  5. It may implement any retrieval or prompting, subject to the answer-path rules above: only the student or a fine-tune of it may produce answers.

The autonomy ladder

Every run is launched on one of three tracks. The set of tracks is called the "autonomy ladder": the axis along which each track gives the agent less input than the one before. Held-out scoring is identical on every track, so a score difference between tracks measures exactly the value of the input that was removed.

  1. easy: the corpus and graded dev questions are given.
  2. medium: the corpus only. The agent must write the dev questions and gold answers it uses to guide its own development.
  3. hard: a one-page brief naming primary sources. The agent must acquire and normalize the corpus itself.

Why "learning as tools"

The agent acts through ordinary shell commands over a versioned learning toolbox: method cards for making training data, pinned training packages, evaluation and serving tools. A tool is a self-describing Python file (its docstring and --help are its documentation). Every action is a traced command, so a completed run can be reconstructed as an exact sequence of steps. Writing a new tool is permitted and is itself a measured behavior. The agent may edit the toolbox. It may not edit the measurement components (pins, judge, held-out data).
