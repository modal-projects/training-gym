The Learning Toolbox

The toolbox is the set of tools the learning agent uses to improve the task agent. It lives at learning_agent_workspace/toolbox/ and is split into five categories. A tool is a Python file: the first line of its module docstring states what it does, and its --help output documents its flags. The observatory registers every file that follows this convention automatically. The agent may rewrite or extend any file in the toolbox. The live catalog is at /tools.

The five categories

  inference_tool/     vllm_serve.py  sglang_serve.py

Three support pieces sit next to the five categories:

  1. api_clients/ — a library for calling LLM and judge APIs. Tools import it. It is never run on its own.
  2. gpu_tools/ — Modal GPU access. gpu_launcher.py runs any self-contained command in a GPU sandbox. gpu_sandbox.py starts an interactive SSH box. The folder also contains platform and training docs.
  3. The cloned packages. toolbox/repos.yaml pins each package to a fixed version, and clone_repos.py clones them into place at setup time.

There is no self-evolution category and no per-tool metadata. The agent is told it may rewrite anything — change harnesses, invent tools — and every conforming file registers itself.

data — make training data

Most data-making methods are not scripts. They are method cards: .md files that state the input/output contract, the recipe, and known pitfalls. The agent reads a card and writes its own generator program; that program then registers as a tool like any other file. The cards are starting points. The agent is expected to vary them, combine them, and invent methods beyond them. Only two data tools ship as runnable programs: pool/dedup_decontam and pool/mix.

  • synthetic/ — cards for generating data grounded in the task corpus: grounded_qa (two-step question-answer generation), paraphrase (WRAP-style rewrites of corpus text in several styles), implications, reasoning, annotation (margin-note glosses), rejection_sampling (sample the student K times, keep the best sample).
  • agentic/ — the react_trace_gen card: generate multi-turn ReAct traces for trace-mode SFT. This is how search behavior is trained into the student.
  • preference/ — the DPO pairs card: sample K completions per question from the current student, judge each against the rubric, and pair the best against the worst when the score gap is large enough. The output is chosen/rejected rows for axolotl's rl: dpo training.
  • pool/ — the two runnable data tools: dedup_decontam (exact and near deduplication, 13-gram decontamination against the eval set over question/gold/rubric text, verbatim seeding; it fails immediately without --eval-questions) and mix (interleave several datasets, balanced by token count).
  • rl/ — the RL data contract: the required shape of the prompts file, and how to write the reward function — either luna as an LLM judge or the agent's own deterministic scoring. The agent owns the reward function.

training — train the task agent's model

training_tool/ contains the training packages themselves, not wrappers around them. Each package is pinned in repos.yaml. The agent drives the packages directly: it reads each package's own docs and recipes, composes that package's commands, and runs them on H200 GPUs with gpu_launcher.py.

  • axolotl/ — config-driven SFT, LoRA, full fine-tuning, and DPO (rl: dpo wraps TRL's DPOTrainer; see its docs/rlhf.qmd).
  • training_gym/ — the Training Gym SDK: RL (GRPO) on Modal, managed (cluster, SGLang rollout engines, checkpoints) with a live dashboard. The agent writes grading rubrics for its own generated questions, uses the pinned gpt-5.6-luna API as LLM-as-judge for the reward, and monitors the run live. Its skills/ folder holds step-by-step playbooks the agent is told to read before driving it.

eval — the agent's own measurement

  • gen_eval — write a development eval set from the corpus. On the medium and hard tracks this dev set is the agent's main progress measure.
  • rubric_eval — score an answers file; the output is a weighted-claim mean plus a confidence interval. api_clients/judge_client is the single-question judge primitive underneath it. Both default to the CANONICAL pinned judge through the judge service when LEARNING_AGENT_JUDGE_URL is set, so dev-time numbers come from the same judge as official scoring (Eval).

harness — the task agent's answering system (pick exactly one)

Rule: a submission answers through one harness, chosen when the submission is wired up. submission/eval.py encodes that choice. Do not mix harnesses within one evaluation: a mixed evaluation makes it impossible to attribute the score margin to any one harness.

There is no package for harness optimization. Improving the student's prompt, search strategy, or tool set — and designing new tools for it — is work the agent does itself. The result is scored on the agent's dev set with the judge, the same way a trained checkpoint is scored.

Assessed and not adopted (2026-08-03): Harbor (laude-institute, the Terminal-Bench harness). It orchestrates containers for agent rollouts and evals. It is an environment layer, not a trainer. The in-repo environment drivers (react_env_agent, mini_swe_agent) cover the bench's environment tasks. Revisit it if rollout scale outgrows them.

There is no self-evolution category. Closed-loop self-improvement is the agent's own behavior, not a tool family. The agent brief states this directly: rewrite your harness, invent tools, keep your own notes. Invocations of the old evolve tools in past runs still classify on the run timeline.

inference — serve the task agent

  • vllm_serve — start an OpenAI-compatible endpoint for a checkpoint using vLLM. sglang_serve — the same using SGLang. These endpoints are what the harnesses and samplers talk to.

The tool contract

  1. A tool is a Python file inside its category folder. Use a folder containing a run.py only when the tool needs several files.
  2. The first line of the module docstring states what the tool does. That line becomes the catalog entry.
  3. --help must work. It is the documentation for the tool's flags.
  4. toolbox/TOOLS.md is the single documentation file: the rules at the top, and a generated catalog below a marker line. python3 observatory/validate_tools.py --emit rewrites the catalog together with the JSON this dashboard serves.
  5. There is no registry. A conforming file IS a registered tool, whether it shipped with the toolbox or the agent wrote it.

Inventing tools

To add a tool:

  1. Write a Python file in the appropriate category folder.
  2. Make the docstring's first line state what the file does.
  3. Make --help work.

That is all. The file is now a registered tool. There is no scaffolding step and no registry to edit. The run timeline records every executed toolbox path automatically, and the catalog regenerates from the files themselves.

Provenance for such a tool defaults to invented (run: <id>), taken from the run id. Conforming invented tools classify onto the timeline and render as cards on the run page and in the catalog, whether or not the trace shows them being executed. Any toolbox/*_tool/ directory counts as a category: known names map to a timeline kind, and a directory the observatory has never seen still classifies as kind tool, refined from the tool's own card in the workspace snapshot. Scripts that do not follow the contract are still detected but appear unstructured.

Rules that hold under every rewrite

  1. The answering model is the designated student model or a fine-tune of it.
  2. No external LLM API in the answer path. API judges are for development-time measurement only.
  3. Training data must derive from the task corpus and the agent's own generations.
  4. The toolbox never edits the pinned surface: harness/ at the repo root, bench.py, the task spec, or the judge (Integrity).
