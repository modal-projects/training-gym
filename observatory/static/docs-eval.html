Evaluation & Scoring

The bench has two evaluation layers. The dev layer belongs to the agent: the agent can rebuild it and judge it however it wants, and its numbers are used only to guide the agent's own work. The test layer belongs to the operator and is frozen: a pinned reference harness, a pinned rubric judge, held-out questions that were never present in any workspace, and a margin over the untrained base model's score.

dev vs test

Each qa-archetype task ships dev.json and test.json with the same row shape: {id, topic, question, gold_answer, rubric, evidence}, where rubric is a list of weighted claims. test.json is deleted from every workspace at seeding; on the medium and hard tracks, dev.json is deleted too. The agent iterates against dev. Only the test score is reported.

The reference harness (base floor + bench.py score)

harness/eval.py serves a checkpoint on Modal (one image per task, with the corpus baked in at /corpus) and runs a fixed ReAct search agent over it. The agent emits actions in this format:

ACTION: {"tool": "grep",      "args": {"pattern": "<regex>", "glob": "<task glob>"}}
ACTION: {"tool": "glob",      "args": {"pattern": "<glob pattern>"}}
ACTION: {"tool": "read_file", "args": {"path": "<path under /corpus>", "start_line": …, "end_line": …}}
FINAL: <task-specific answer hint>

Tool output is truncated to keep the context bounded: grep returns at most 40 hits, glob at most 80 files, read_file at most 200 lines. The model searches until it emits FINAL, typically after about 8 tool calls. The pinned eval_budget: 50 is an upper limit on tool calls, not a step count runs are expected to reach. Decoding uses temperature 0. Candidate answers are written to runs/<tag>/budget_<b>/candidates.json as {id: answer}. submission/eval.py writes the same format, so operator scoring judges both sources with the same code.

The rubric judge

harness/judge.py scores one candidate answer against one row's weighted claims. The judge receives the question, the gold answer, the rubric, and the candidate answer. It returns strict JSON verdicts, one per claim. The scoring rules:

  1. Per-claim scoring is binary: 1 if the claim is satisfied, 0 if not. 0.5 is allowed only when a claim has genuinely separable parts. Vague references and hedged non-answers earn no credit. Some claims name both a correct approach and a decoy; only the correct one earns credit.
  2. The question score is the weighted mean over claims. The run score is the mean over questions.
  3. Every question is judged n_votes: 3 times at temperature 0 with forced structured output (function-call/tool schema). The per-claim result is the majority vote, with the median on ties.
  4. A failed judge call never counts as a zero score. 429/5xx/parse failures retry 3 times with backoff. A question that still fails is recorded failed: true and excluded: the run score is the mean over judged questions, or null if all questions failed. A run where all questions failed writes no leaderboard row.
  5. Uncertainty is reported as a 95% bootstrap confidence interval over question scores: 10,000 resamples, seed 0. The CI reproduces bit-identically.
  6. Each task also has a deterministic secondary check (python_compiles, ts_symbol_grounding, or edgar_ref_grounding). It is reported next to the rubric mean and is never combined with it (grade_mode: lenient).

Judge backends and canonicality

backendtransportcanonical?
openaiOpenAI Chat Completions with forced function-call output; pinned snapshot gpt-5.6-luna yes, when the model equals the pin
apiAnthropic Messages with forced tool schema; pinned snapshotyes, when the model equals the pin
cli-claude / cli-codexlogged-in CLI sessions no. Sampling is uncontrolled, so results are stamped canonical: false. Usable for dev signal; not comparable across machines.

Every result embeds full provenance: judge model and pinned model, backend, vote count, judge-prompt hash, harness hash, sys/gold/config hashes, corpus pin, budget, temperature, seed, integrity status, and timestamp. To check whether two numbers are comparable, diff their provenance. A judge model other than the pin runs normally but is stamped canonical: false. Smoke runs (--limit) write smoke_* artifacts and never write the full-run result files.

The judge service

Sealed workspaces contain no provider API key. Before the judge service existed, in-run dev evals therefore fell back to CLI judges (canonical: false) — a different judge than the one used for scoring, and dev and test numbers diverged. harness/judge_service.py removes that mismatch, using the same pattern as the user simulator for conversational tasks: the operator runs the service, the service holds the OpenAI key, and it serves the single pinned judge model (gpt-5.6-luna) over an OpenAI-compatible endpoint. Whatever model name a caller sends is ignored. Each workspace gets LEARNING_AGENT_JUDGE_URL and a revocable LEARNING_AGENT_JUDGE_TOKEN in its .env, and the toolbox judge loads them automatically. The agent's dev-set evals, and its intermediate-checkpoint evals during training, therefore run on the same judge that scores the submission, stamped canonical: true.

  1. Model pinning is server-side. The caller cannot change the judge model.
  2. Each session has a completion-token budget cap. The endpoint grades rubrics; it is not a general-purpose model API. Every call is logged with session, token cost, and a request fingerprint.
  3. The evaluation boundary is unchanged: the answer path still makes no external LLM calls, and the trace audit checks for violations after every run.
  4. Deploy: modal secret create lab-judge-secrets OPENAI_API_KEY=… LEARNING_AGENT_JUDGE_TOKEN=…, then modal deploy harness/judge_service.py. /health reports the model and revision.

Margins

The reported number for a run is margin = submission_mean − base_floor_mean. The base floor is the score of the untrained base model (Qwen3.5-9B) run through the reference harness, judged by the same judge configuration in the same scoring session as the submission. A floor scored under a different judge is not a valid comparison point; when the judge changes, re-judge the floor.

Scoring a finished run, step by step

# 1. questions only (ids + text) from the held-out set
python3 - <<'EOF'
import json; t=json.load(open("tasks/<task>/test.json"))
json.dump([{"id":r["id"],"question":r["question"]} for r in t], open("q.json","w"))
EOF
# 2. the submission answers them (the agent's own serving + retrieval)
cd agents/_runs/ws_<run>/workspace && python submission/eval.py --input q.json --output answers.json
# 3. wrap as candidates and judge (same judge for submission AND floor)
mkdir -p runs/<sub_tag>/budget_50 && cp answers.json runs/<sub_tag>/budget_50/candidates.json
python3 harness/judge_cli.py --task <task> --tag <sub_tag>     --split test --backend openai
python3 harness/judge_cli.py --task <task> --tag base_floor_test --split test --backend openai
# 4. append the run-level margin row to runs/LEADERBOARD.jsonl; publish to the dashboard
python3 -m observatory.cli sync-scores

Dev-vs-test calibration

Runs that predate the judge service self-reported dev scores judged by whatever judge the agent built: a different model, a different vote count, a different scale. Those numbers are not comparable across runs, and they routinely sat far above the held-out score (observed: dev 0.372 → test 0.069, and dev 0.562 → test 0.252 on the same task). With the judge service available in the workspace, dev scores judged through it use the same judge as scoring, so any remaining dev-vs-test gap measures question difficulty and gold-answer quality, not judge mismatch. On the medium and hard tracks the agent wrote its own gold answers, so that gap is itself part of what the benchmark measures: building a trustworthy eval is scored behavior. The dashboard flags self-reported dev scores and shows both columns side by side.
