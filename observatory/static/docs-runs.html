Runs & Observability

Every run uses the same launch shape, and every run — live or finished — is normalized into the same record structure this dashboard renders: events, sessions, scores, the learning timeline, telemetry, and the workspace itself.

Where a run executes

runnerexecutes onworkspace lives at
agents/run_sandbox_modal.sh a container under Modal app lab-agent, one per session volume lab-agent-workspace: <task>/<session>/workspace
agents/run_sandbox_docker.sha local Docker container agents/_container_runs/<task>/<session>/workspace

Agents never execute as bare processes on the operator machine. The historical local runner, agents/run_sandbox.sh, is retired. Runs before 2026-08-11 were launched with it; their records live on the observatory volume.

All runners share the launch shape <scaffold> <task> [hours] [model] and one seeding routine, so the sandbox is identical wherever it runs. Container sessions also carry:

  1. <task>/<session>/logs, a directory beside the workspace. HOME points inside it, so the CLI's native session state persists with the run record.
  2. A Modal token, so in-container training jobs and live ingest work.

Modal budgets clamp to 23.75 h: the platform's 24 h container ceiling must outlive the runner's grace kill. The agent's model calls go to its API endpoint. Its GPU jobs always go to Modal. Local runs require the operator machine to stay awake.

Live ingest

A watcher (observatory.cli watch) checks the run every 30–60 s. On each pass it:

  1. stamps an arrival time on each new trace line;
  2. samples CPU and memory (Modal GPU jobs add their own telemetry via the drop-in sampler);
  3. rebuilds the record and uploads it.

The final pass is triggered by solve_status.txt. It archives the workspace as raw/workspace.tar.gz (excluding corpus, .git, and venvs), so anyone can pull a finished submission and score it without the machine that ran it. Local runs opt in with --watch. Container runs always watch themselves, using a read-only seed copy of the observatory code, so the agent cannot rewrite its own reporter.

The run record

Every scaffold's trace normalizes into one schema, defined in observatory/schema.py. A record contains:

  1. index_row — state, task, scaffold, track, best dev score, learning counts, canonical/integrity/audit flags, cost, and duration.
  2. events — each with hoisted content blocks (thinking / text / tool_use / tool_result), so one rendering path serves every harness.
  3. sessions.
  4. scores — the workspace's checkpoint ledger, leaderboard rows, and every results file the run produced.
  5. judgements — the audit verdict.
  6. system_monitor — telemetry samples.
  7. learning — the timeline described below.

The learning timeline

Every traced shell command is classified against the tool registry (two pattern families) into a LearningAction. Each action records:

  1. the kind: data | train | eval | evolve | tool;
  2. the tool identity and the full command;
  3. extracted flags (--tag, --rows, …);
  4. nth_use — a per-tool reuse counter in event order;
  5. provenance: seed (the command matched a registry pattern), invented (an executed script absent from the run's seed manifest but present in the final workspace snapshot), or unknown (runs predating seed manifests).

A temporary script deleted before run end is deliberately not counted. The run page renders this timeline; the index shows per-kind counts.

Dev and test columns

The runs table shows two score columns:

  1. dev is self-reported. It is the best harness dev result if the workspace produced one, otherwise the best dev_score in the agent's checkpoint ledger (the fallback has no CI).
  2. test is official. sync-scores uploads the operator leaderboard, and run-level rows (run id + submission mean) overlay onto the table, with the margin in parentheses and the judge in the tooltip. Re-scorings supersede earlier ones: later rows win.
