Integrity Model

A benchmark number is meaningful only if the measurement code and data were identical across runs and the agent had no access to the held-out data. The bench enforces both mechanically: content hashes cover every file that defines the measurement, and held-out files are physically absent from workspaces.

Pins

bench/pins.json stores a sha256 hash for every file that defines the measurement: the harness code (eval.py, judge.py, judge_cli.py, grader.py, integrity.py itself, envfile.py), bench.py, bench/config.yaml, the contestant template AGENTS.md and the three track blocks, and per task: task.yaml, sys.txt, dev.json, test.json, task.md, brief.md, the secondary-metric data files, and the corpus as a content tree-hash (volatile entries excluded). The judge prompt is additionally pinned as a hash of its source function, so an edit to the prompt is detected even if the file that contains it moves.

  1. python bench.py verify reports drift against the pins. It exits 0 if and only if everything matches.
  2. python bench.py freeze re-records the pins after an intended change. Freeze is strict: every pinned file must exist, because a partial tree cannot define the benchmark.
  3. Scoring refuses to run when pins do not match. score and judge verify pins first. --allow-dirty overrides the check but stamps integrity: DIRTY into the provenance and the leaderboard row, permanently.
  4. harness/integrity.py is itself pinned. The pinned entrypoints hash it directly against pins.json before calling its verify_pins function, so a modified verifier is detected by its callers instead of being trusted to check itself.
Team rule: any commit that touches a pinned file includes the freeze re-pin in the same change. Every drift incident so far was a forgotten freeze, caught by the six integrity tests that assert a clean surface.

Workspace sealing

Agents never run in the seed repository. agents/run.sh refuses to start unless the .learning_agent_sandbox marker file is present, and only the sandbox preparation writes that marker. Seeding (agents/lib/prepare_workspace.sh, the same script used verbatim by the local, Modal, and Docker runners) does the following, in order:

  1. Runs git archive HEAD on learning_agent_workspace/. The agent surface (AGENTS.md, toolbox, submission, ledgers) becomes the workspace root. Seeding also copies in the run machinery (agents/run.sh plus its lib and the one chosen scaffold), the prompt material (bench/config.yaml, bench/tracks/), and the one task's committed files. Only the committed tree is exported: no .git directory and no history, and no harness/, observatory/, or bench.py at all.
  2. Deletes the seeded task's test.json; on medium and hard, also its dev.json. Held-out data is absent from the workspace, not hidden in it, and other tasks' material never enters the workspace in the first place.
  3. Truncates runs/LEARNING_LOG.jsonl. A fresh workspace carries no output from earlier runs: earlier generations' scores and methods must not leak into a run that is supposed to discover its own.
  4. Seeds the gitignored inputs for the track (the corpus, and dev gold on easy) and a .env with all API keys stripped. Operator judge credentials are used for end-of-run scoring only and never enter a workspace.
  5. Writes the sandbox marker; a seed manifest (git ls-tree over exactly the seeded file set, with workspace-relative paths — the baseline used to detect tools invented during the run); and run metadata. Then runs git init to create a fresh history so the agent can version its own work.

Trace audit

After every run, agents/lib/audit_trace.py scans the full trace for any attempt to reach held-out evaluation data. It checks path patterns, quoted content, and exfiltration shapes. It is a deterministic scanner, not an LLM. The verdict is stored with the run record and on the leaderboard as audit: CLEAN or CONTAMINATED; a hit invalidates the run.

Corpus construction

For new tasks, held-out material is kept out of the corpus by how the corpus is built. The pack builder publishes two separate artifacts: the evaluation file (questions, options, gold answers) and the source-only corpus. The corpus builder stops with an error if any evaluation key appears anywhere in its input tree. Filtering after the fact (n-gram decontamination) is a data-cleaning tool; it is not the containment mechanism. Containment comes from building the two artifacts separately.

Result provenance

Every scored result records: judge model and pinned model, backend, canonical flag, vote count, judge-prompt/harness/sys/gold/config hashes, corpus pin, eval budget, temperature, seed, integrity status, and timestamp. The leaderboard (runs/LEADERBOARD.jsonl) is append-only: re-scorings append new rows instead of editing old ones, and run-level margin rows name the run id they score.

Known open issues

  1. Shared-volume tag collisions. Trained weights live in a flat namespace on lab-out, so a run that reuses another run's tag overwrites that run's artifact. The planned fix is per-run namespacing of /out/models/. Until then, use run-unique tags.
  2. Public viewer. This dashboard is deliberately public and unauthenticated (a v1 decision). Everything ingested to the shared volume is world-readable, including workspace archives. Before ingesting a run, check whether its workspace embeds proprietary gold answers.
  3. Dev-signal dependence on local CLIs. Agents that judge themselves through logged-in CLI sessions lose that judge in containerized runs. The endpoint-backed judge in the toolbox is the replacement.
